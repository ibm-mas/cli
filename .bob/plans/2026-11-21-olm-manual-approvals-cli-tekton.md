# OLM Manual Install Plan Approvals — CLI & Tekton Pipeline Support

**Status:** Implemented on `manualsubs` (2026-11-23) — all phases except cluster
end-to-end verification (see Verification below) and Phase 4 branch-build confirmation,
which requires the CI branch pre-release image build.
**Branch:** `manualsubs` (same branch name in cli, ansible-devops, python-devops per CONTRIBUTING.md cross-repo rule)
**Date:** 2026-11-21

## Context

The ansible-devops collection (`manualsubs` branch) now supports manual OLM install plan
approvals: with `OLM_APPROVAL_MODE=Manual` (and `OLM_APPROVAL_TIMEOUT`, default 7200s),
roles pause with human-facing instructions whenever an install plan awaits approval,
wait for the out-of-band approval (5-minute status lines showing the deadline), then
resume — or fail when the timeout expires. The collection never approves on the user's
behalf. Support covers the `apply_subscription` path (~20 roles), the template-based
dependency roles, the update/upgrade channel-change flows, and a cluster-wide approval
gate in `ocp_verify` (this is where `mas update`'s implicit catalog-digest subscription
rolls are waited on).

The python-devops library (`manualsubs` branch) provides the underlying primitives and
has been aligned so Mixed approval-mode namespaces behave the same as Manual.

What's missing is the **choice**: nothing in the CLI or its Tekton pipelines exposes
approval mode to the user. This plan wires `OLM_APPROVAL_MODE` / `OLM_APPROVAL_TIMEOUT`
end-to-end:

```
mas install --olm-approval-mode Manual
  → CLI params dict
    → PipelineRun param (python-devops pipelinerun-*.yml.j2)
      → Pipeline param (cli/tekton/src/params/common.yml.j2)
        → PipelineTask param (taskdefs/common/cli-params.yml.j2)
          → Task stepTemplate env OLM_APPROVAL_MODE (tasks/common/cli-env.yml.j2)
            → ansible role (already implemented in ansible-devops@manualsubs)
```

### Key facts established by exploration

- **The Tekton bundle is generated — never hand-edit `ibm-mas-tekton.yaml`.** Sources:
  `cli/tekton/src/{params,tasks,pipelines}` (+ `pipelines/taskdefs/`), regenerated by
  `make tekton` (`build/bin/build-tekton.sh`), which updates BOTH copies
  (`python/src/mas/cli/templates/` and `image/cli/mascli/templates/`).
- **Chokepoints exist.** Every pipeline includes `params/common.yml.j2`
  (`image_pull_policy` etc. live there); role-running tasks include
  `tasks/common/cli-params.yml.j2` + `tasks/common/cli-env.yml.j2`; taskdefs include
  `taskdefs/common/cli-params.yml.j2`. Coverage: 56/189 task files include cli-env,
  66/127 taskdefs include the common params — a post-generation verification step is
  needed for stragglers (see Phase 3).
- **Empty-string env resolves to Automatic — and the mismatch fast-fail is the
  default.** The collection's `resolveApprovalMode`/`resolveApprovalTimeout`
  (ansible-devops `plugins/module_utils/olm_approvals.py`) treat an empty-string
  env value as unset, and an unset mode resolves to **Automatic** (there is no
  "unset" third state). The managed-subscription mismatch check in
  `apply_subscription` runs on every call: re-applying a `Manual` subscription
  with no mode set fails fast with instructions instead of slow-failing in the
  operator readiness waits (ansible-devops commit `b9245a5`, deliberate bug fix).
  The same fast-fail applies in `ocp_verify` (unconditional approval gate:
  waits under Manual, fails fast with the approve commands under Automatic,
  no-op when nothing is pending). So pipeline params can default to `""` and
  the env entries can be unconditional: default runs behave as today on
  healthy clusters, and misconfigured Manual states fail fast by design.
- **Task timeouts are all `timeout: "0"`** and PipelineRun `timeouts.pipeline: "0"` —
  multi-hour in-role approval waits fit with no timeout changes anywhere.
- **Naming:** `--approval-*` is already taken by the ConfigMap-based pipeline
  checkpoint workflow (`--approval-core`, `--approval-manage`, ... in
  `install/argParser.py:1621-1676`). The OLM flags must be `--olm-approval-mode` /
  `--olm-approval-timeout` to avoid ambiguity with that existing (unrelated) mechanism.
- **The CLI is fire-and-forget** (`launch*Pipeline` applies the PipelineRun and returns
  a console URL; no log streaming/status polling). Users watch approvals in the
  OpenShift console / task logs. No CLI-side waiting code is needed for this plan.
- **Precedent patterns to follow:** enum flag with `choices` + `metavar`
  (`--dns-provider`, install/argParser.py:223-230); pipeline string-boolean with
  `when: notin ["True","true"]` (`skip_pre_check`); conditional PipelineRun param
  emission (`{% if x is defined and x != "" %}` in the pipelinerun j2 templates);
  prompt defaults read from the uppercased param name env var (displayMixins.py:185).

## Design

### CLI surface

The distinction between the commands is deliberate: **in install the user is
informing the CLI how to set things up; in update/upgrade the CLI is reminding
the user how they set things up.**

#### mas install — the user's choice

New "OLM Install Plan Approval" argument group:

- `--olm-approval-mode {Automatic,Manual}` — `choices=["Automatic", "Manual"]`,
  `metavar="{Automatic,Manual}"`, default None (not set).
- `--olm-approval-timeout <seconds>` — `type=int`, default None. Seconds, matching the
  collection's `OLM_APPROVAL_TIMEOUT` (default 7200 = 2 hours, budgeting each
  individual approval wait).

Precedence: **flag > `OLM_APPROVAL_MODE`/`OLM_APPROVAL_TIMEOUT` shell env > omitted**.
After parsing, if the flag is unset, fall back to the shell env var (validate the mode
value and fatal on a bad value with a message naming the env var — mirror the
collection's message). This keeps the CLI consistent with the collection's
modules-read-env-directly convention: a user who already exports `OLM_APPROVAL_MODE`
gets Manual installs without new flags. When neither flag nor env is set, the params
are simply omitted from the PipelineRun (pipeline defaults `""` apply → effective
mode Automatic).

`--olm-approval-mode Automatic` and omitting the flag are **the same thing**: both
mean Automatic. Under Automatic the collection fails fast when the subscription it
manages is `Manual`, or when install plans are pending (the `ocp_verify` gate) — this
fast-fail is the intended default behavior (bug fix: these states used to slow-fail
in the readiness waits). Document this in the flag help.

**The install wizard prompts for approval mode**: add prompts to the install
settings mixins — `promptForListSelect` for the mode (Automatic/Manual, default
`Automatic`, picking up the `OLM_APPROVAL_MODE` env var as the default via the
displayMixins convention), and when Manual is selected, `promptForInt` for the
timeout (default 7200, `OLM_APPROVAL_TIMEOUT` env default). If the install TUI
renders its own settings screens, add the choice there too.

#### mas update / mas upgrade — detected and reported, not chosen

No `--olm-approval-mode` flag and no `OLM_APPROVAL_MODE` env fallback on these
commands: the mode was chosen at install time and is a property of the cluster.
The detection scope matches each command's blast radius — a single subscription
(the core one included) can never represent it:

- **mas update** inspects the **whole cluster**: update rolls every IBM catalog
  subscription via the catalog digest change, so the aggregate is taken across
  all Subscriptions in all namespaces.
- **mas upgrade** inspects **all `mas-{instance_id}-*` namespaces** (core and
  application namespaces): the upgrade is scoped to these, and even within them
  the core subscription cannot be assumed to represent the applications.
  (The `aiservice-{instance_id}` namespace belongs to the separate
  aiservice-upgrade pipeline — out of scope here.)

Detection aggregates the effective mode (`spec.installPlanApproval`, unset =
`Automatic`) of every Subscription in scope and reports:

- `Automatic` — every subscription in scope is Automatic.
- `Manual` — every subscription in scope is Manual.
- `Mixed` — both modes present, reported with counts
  (e.g. `Mixed (40 Automatic, 2 Manual) — treating as Manual`).

Before submitting the PipelineRun the CLI:

1. **Detects** the aggregate mode over the command's scope (new python-devops
   helper, e.g. `getClusterApprovalMode(dynClient, namespacePrefix=None)` —
   cluster-wide for update, `mas-{instance_id}-` prefix for upgrade; see
   Phase 1).
2. **Reports** it in the settings summary (and the update/upgrade TUI review
   screen), e.g. `OLM install plan approval: Manual — install plans generated
   by this update will wait for your approval`. This is the reminder of how
   the user set things up.
3. **Passes** the effective mode to the PipelineRun (`olm_approval_mode`) so
   the pipeline behaves consistently with the cluster: detected Manual → the
   approval gates wait; detected Automatic → the default fast-fail behavior;
   **Mixed → Manual** (consistent with the collection's Mixed-is-Manual
   semantics: the approval gates wait, while the Automatic subscriptions roll
   freely).

**Mixed clusters and the mismatch fast-fail (ansible-devops follow-up,
required):** under a Mixed aggregate the update passes `Manual`, but the update
path re-applies some subscriptions (e.g. `update-db2` via `apply_subscription`)
whose existing mode is `Automatic` — the current symmetric mismatch check
would fast-fail those with no CLI remedy (update accepts no mode flag). The
check must become **asymmetric** (owner-confirmed semantics):

- **Mode Manual or Mixed** + existing subscription is `Automatic` → **warn**
  ("existing subscription X is set to Automatic, but OLM approval mode is
  Manual") and **preserve** the subscription's Automatic mode — it keeps
  rolling freely; we do not flip it.
- **Mode Automatic** (including unset, which resolves to Automatic) + existing
  subscription is `Manual` → **fatal**: we cannot turn off manual approvals
  (this is the slow-fail bug being fixed — the error names the subscription
  and the `OLM_APPROVAL_MODE` remedy).
- Explicit `install_plan_approval` task arguments remain imposing and fail on
  conflict in both directions.

This keeps Mixed clusters updatable (each operator updates according to its
own subscription's mode, while the Manual ones gate on approval) without
weakening the protection: nothing can silently remove human gating.

`--olm-approval-timeout` **is** available on update/upgrade (a wait budget is an
operational choice, not a setup choice), with the `OLM_APPROVAL_TIMEOUT` env
fallback; when unset the collection default (7200s) applies. `olm_approval_mode`
is set programmatically from detection — it is NOT in the update/upgrade
`optionalParams`.

#### Not in scope for flags

`aiservice-install` / `aiservice-upgrade` / `uninstall` / `backup` / `restore`:
the pipelines pick the params up for free via `params/common.yml.j2` (inert
unless set). Backup/restore pre-checks (`ocp-verify`) fast-fail when install
plans are pending (by design: a cluster with pending approvals is not settled);
they do not wait for approvals.

### python-devops (branch `manualsubs`) — PipelineRun templates

`src/mas/devops/templates/pipelinerun-install.yml.j2`,
`pipelinerun-update.yml.j2`, `pipelinerun-upgrade.yml.j2` — add conditionally-emitted
params following the existing pattern:

```yaml
{% if olm_approval_mode is defined and olm_approval_mode != "" %}
- name: olm_approval_mode
  value: "{{ olm_approval_mode }}"
{% endif %}
{% if olm_approval_timeout is defined and olm_approval_timeout != "" %}
- name: olm_approval_timeout
  value: "{{ olm_approval_timeout }}"
{% endif %}
```

No `launch*Pipeline` code changes needed (params pass through `**params`). The CLI is
responsible for validating values before launch (argparse `choices` + env fallback
validation).

### cli/tekton/src — pipeline params, task params, task env, taskdefs

Four partial edits (the whole plumbing change):

1. **`src/params/common.yml.j2`** — new pipeline params (included by every pipeline):
   ```yaml
   # OLM install plan approval: "Manual" pauses roles at every install plan awaiting
   # human approval (see ansible-devops OLM manual approvals). Empty = Automatic
   # (the collection treats an empty env value as unset, which resolves to Automatic
   # with the mismatch fast-fail active by default).
   - name: olm_approval_mode
     type: string
     default: ""
     description: OLM install plan approval mode (Automatic or Manual); empty defaults to Automatic
   - name: olm_approval_timeout
     type: string
     default: ""
     description: Seconds to wait for each individual install plan approval under Manual mode (collection default 7200)
   ```
2. **`src/tasks/common/cli-params.yml.j2`** — the same two as Task `spec.params`
   (string, default `""`).
3. **`src/tasks/common/cli-env.yml.j2`** — the env entries, exactly like `MAS_CHANNEL`:
   ```yaml
   - name: OLM_APPROVAL_MODE
     value: $(params.olm_approval_mode)
   - name: OLM_APPROVAL_TIMEOUT
     value: $(params.olm_approval_timeout)
   ```
4. **`src/pipelines/taskdefs/common/cli-params.yml.j2`** — passthrough:
   ```yaml
   - name: olm_approval_mode
     value: $(params.olm_approval_mode)
   - name: olm_approval_timeout
     value: $(params.olm_approval_timeout)
   ```

Then regenerate (`make tekton`) and **verify coverage**: every task whose step calls
`/opt/app-root/src/run-role.sh` must have the `OLM_APPROVAL_MODE` env (grep the
generated bundle). Tasks/taskdefs that do NOT include the common partials (56/189 and
66/127 coverage today) need the entries added directly — expected stragglers to check:
`ocp-verify`/`ocp-verify-all`, `ibm-catalogs`, dependency install tasks
(cert-manager/grafana/eck/kafka/db2/sls/dro/cp4d/nvidia-gpu), `suite-install`,
`suite-app-install`, `app-*-upgrade`, `core-upgrade`, `update-*` tasks. Consider
adding a bundle test (Phase 5) so coverage can't regress.

### Relationship to the existing waitfor-approval gates

The ConfigMap-based `waitfor-approval` task in mas-update/mas-upgrade
(`approval-update`/`approval-upgrade`, opt-in by ConfigMap existence) and the install
`--approval-core/--approval-*` checkpoint workflow are a **different, complementary
mechanism** (pipeline-level human gates between stages). OLM approval mode gates
individual install plans inside roles. No changes to the ConfigMap workflow; document
the distinction in the guides so users know which to reach for.

## Verification

1. **Unit**: `make pytest` (cli), `make test` (python-devops), `pytest-tekton` (cli).
2. **Generated bundle**: after `make tekton`, `grep -c "OLM_APPROVAL_MODE"` across the
   bundle matches the run-role task count; `grep -B2 -A2 'name: olm_approval_mode'`
   shows the params on all 7 pipelines.
3. **End-to-end on a cluster** (all three repos on `manualsubs`, branch pre-release
   CLI image):
   - Default regression: `mas install` without flags → PipelineRun has no
     `olm_approval_mode` param; task env `OLM_APPROVAL_MODE=""`; on a cluster with
     no Manual subscriptions the run behaves identically to today (subscriptions
     applied with explicit Automatic).
   - Default fast-fail (the bug fix): with no flags, against a cluster where a
     subscription the collection manages is Manual (or install plans are pending),
     the run fails fast with the mismatch error and the approve commands /
     `OLM_APPROVAL_MODE=Manual` remedy — not a hang in the readiness waits. The same
     happens with `--olm-approval-mode Automatic` (explicit and omitted are
     equivalent).
   - `mas install --olm-approval-mode Manual` (or `OLM_APPROVAL_MODE=Manual mas
     install`, or the wizard prompt) → PipelineRun carries the param; task env
     `Manual`; roles pause with the approval notices (ibm-sls must NOT fatal on
     the `ibm-truststore-mgr` Mixed namespace); approve out-of-band with the printed
     `oc patch` command or the OpenShift console; roles resume; install completes.
   - `mas install --olm-approval-mode Manual --olm-approval-timeout 300` + never
     approve → role fails with the actionable timeout error; pipeline task fails;
     PipelineRun shows Failed.
   - **Detection (update)**: cluster installed with Manual → `mas update` (no flags)
     → summary reports the detected Manual mode → PipelineRun
     `olm_approval_mode=Manual` → catalog roll gates at `post-update-verify`
     (cluster-wide wait in ocp_verify) and `post-deps-update-verify`; approve;
     update completes.
   - **Detection (upgrade)**: cluster installed with Manual → `mas upgrade` →
     detection reports Manual → channel bumps gate per the suite_upgrade/app
     upgrade approval waits.
   - **Detection (Automatic)**: cluster installed with Automatic → `mas update`
     reports Automatic → default fast-fail behavior on any pending/Manual state
     (same as omitting the mode on install).
   - **Mixed cluster (update)**: a cluster with some Manual and some Automatic
     subscriptions → `mas update` reports `Mixed (N Automatic, M Manual) — treating
     as Manual` → PipelineRun `olm_approval_mode=Manual` → approval gates wait for
     the Manual subscriptions' install plans while Automatic subscriptions roll
     freely; re-applied subscriptions whose existing mode is Automatic are
     preserved with a warning (no mismatch fatal — validates the asymmetric
     collection refinement).
   - **Mixed cluster (upgrade)**: Mixed aggregate across the `mas-{id}-*`
     namespaces → same treatment, scoped to those namespaces; subscriptions
     outside the scope (dependencies) are neither inspected nor mode-affected.
   - Explicit `--olm-approval-mode Automatic` against a Manual subscription →
     fail-fast mismatch error naming the subscription (validates the pre-check path;
     the same fast-fail must also occur with the flag omitted).
4. **Tekton cluster validation** per CONTRIBUTING (cli/tekton: `oc login`, generate
   playbooks, `./test.sh`).
