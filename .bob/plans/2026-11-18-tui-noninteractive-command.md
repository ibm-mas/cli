# Plan: Wire the non-interactive command generation (PR #2713) into the TUI update flow

## Context

PR #2713 (merged to master, merged into `textual-update` in decd9b5941) added a data-driven
non-interactive command builder and enabled it for `mas update`:

- `python/src/mas/cli/common/commandBuilder.py` — generic `CommandArg` spec + `renderCommand()`, plus `copyToClipboard()` and `offerCommandScript()` helpers
- `python/src/mas/cli/update/argBuilder.py` — `UPDATE_COMMAND_ARGS` spec and `updateArgBuilderMixin.buildCommand()` (round-trip tested in `python/tests/unit/update/test_update_arg_builder.py`)

In the classic interactive flow, `UpdateApp.update()` ([app.py:347-358](python/src/mas/cli/update/app.py#L347-L358)) prints the
command before the review screen, offers clipboard-copy / save-as-script, and re-prints it after
pipeline launch ([app.py:412-420](python/src/mas/cli/update/app.py#L412-L420)). The Textual TUI flow bypasses
all of that (`serveTuiMode` drives the steps directly), so the capability is absent from the TUI —
this is "Phase 4" of the plan in `.bob/plans/2026-11-17-install-command-builder.md`, intentionally
deferred to this branch.

**Goal (user confirmed: full parity):** show the generated command on the review screen before
Confirm & Launch, with Copy Command and Save Script buttons, and re-display it (with copy) on the
launch screen after the pipeline is submitted.

## Design decision

The deferred plan sketched `WorkflowField.cli_flag` + generic rendering from workflow fields. We
**don't** do that: the update workflow's fields cover only a fraction of the command (most flags
come from auto-detected params and the confirm-upgrades step, which have no `WorkflowField`), so a
field-derived command would be nearly empty and would duplicate the spec. Instead the TUI calls the
already-round-trip-tested `UpdateApp.buildCommand()` through a `command_builder` callable passed via
`screen_kwargs` — the same mechanism `review_builder` already uses. The screens stay generic; `mas
update` is the first consumer; any future TUI flow with an argBuilder mixin inherits the feature by
passing one kwarg.

## Changes

### 1. Shared helper — `python/src/mas/cli/common/commandBuilder.py`

Add `writeCommandScript(filename: str, command: str) -> None`: writes
`#!/bin/bash\n# Generated by the MAS CLI interactive wizard\n\n` + command (raises `OSError` to the
caller). Refactor `offerCommandScript()` to use it so the file format has one owner.

### 2. Review screen — `python/src/mas/cli/tui/screens/review.py`

- Constructor gains two optional kwargs (shell already forwards `**screen_kwargs`,
  [shell.py:210](python/src/mas/cli/tui/shell.py#L210)):
  - `command_builder: Optional[Callable[[Any], str]]` — renders the command from the app
  - `script_filename_builder: Optional[Callable[[Any], str]]` — default filename for Save Script
- `compose()`: inside the `VerticalScroll`, after the Markdown widget, add a bordered command panel
  (`Vertical #review-command-panel` with a caption Label and `Static #review-command-text`). Add
  `Copy Command` (`#btn-copy-command`) and `Save Script` (`#btn-save-script`) buttons to the
  ActionBar ahead of Confirm & Launch.
- `on_mount()`: hide the panel and both buttons when `command_builder` is None (Save Script also
  hidden when `script_filename_builder` is None); otherwise hide nothing.
- `start_dynamic_loaders()`: refresh the Markdown as today **and** regenerate the command text, so
  re-visiting the step after going back reflects current params.
- `on_button_pressed()`:
  - Copy Command → `copyToClipboard()` (imported from `mas.cli.common.commandBuilder`; graceful
    no-op without pyperclip), feedback via `ActionBar.set_status()` ("Command copied to clipboard" /
    "Clipboard is not available in this environment")
  - Save Script → `writeCommandScript(filename, command)` with the filename from
    `script_filename_builder(mas_app)`; status "Script saved to <file>", `set_error()` on OSError

### 3. Launch screen — `python/src/mas/cli/tui/screens/launch.py`

- Constructor gains optional `command_builder` kwarg.
- `compose()`: after the `#pipeline-url` Label add `Label #launch-command-caption` ("For reference,
  the non-interactive command equivalent to this update:") and `Static #launch-command-text`; add a
  `Copy Command` (`#btn-copy-command`) button next to Copy URL. All hidden on mount (same pattern as
  the existing hidden buttons).
- Success path: in `_run_launch()`, alongside `self._enable_done`, `call_from_thread` a
  `_show_command_reference()` that populates and reveals the caption/text (via
  `command_builder(self._mas_app)`) and the Copy Command button. Nothing shown on failure.
- Copy Command handler mirrors the existing Copy URL handler ("Copied!" label + 2s timer), using
  `copyToClipboard()` from the common module.

### 4. Update workflow wiring — `python/src/mas/cli/update/workflow.py`

Module-level callables (mirroring [app.py:358](python/src/mas/cli/update/app.py#L358)):

```python
def _nonInteractiveCommand(appInstance): return appInstance.buildCommand()
def _scriptFilename(appInstance): return f"mas-update-{appInstance.getParam('mas_catalog_version')}.sh"
```

- `reviewStep.screen_kwargs`: add `command_builder=_nonInteractiveCommand`,
  `script_filename_builder=_scriptFilename` (keeping `review_builder=buildUpdateReview`)
- `launchStep.screen_kwargs`: add `command_builder=_nonInteractiveCommand`

### 5. Styles — `python/src/mas/cli/tui/styles/app.tcss`

In the ReviewScreen section: `.command-panel` (bordered round panel, mirroring the existing
`.step-context` / `.confirm-section` treatment: `margin-top: 1; padding: 1; border: round
$panel-lighten-2`), muted caption label, and `text-wrap: wrap` on the command Static so long
continuation lines wrap instead of clipping.

## Tests (per `python/AGENTS.md` placement rules)

1. **`python/tests/unit/update/test_update_workflow.py`** (extend, follows existing style):
   - review step `screen_kwargs` carries a `command_builder` that delegates to `buildCommand()`
     (mock app, sentinel return) and a `script_filename_builder` producing `mas-update-<catalog>.sh`
   - launch step `screen_kwargs` carries the `command_builder`
   - sanity: builder output against a real scenario app (`tests/scenarios/update.py`,
     `update_scenario("clean")` + `mas_catalog_version` param) starts with `mas update \` and
     contains `--no-confirm`
2. **`python/tests/pilot/tui/test_review_screen.py`** (new — ReviewScreen is generic framework):
   - command panel renders the builder output; panel + buttons hidden when no builder
   - Copy Command invokes the copied text (monkeypatch `mas.cli.tui.screens.review.copyToClipboard`)
   - Save Script writes the shebang header + command to `tmp_path` and shows the saved status
   - Confirm still posts `step_completed`
3. **`python/tests/pilot/update/test_launch_screen.py`** (extend `_make_screen` to accept
   `command_builder`): successful launch reveals the reference caption + command text, and Copy
   Command copies the command (monkeypatch `mas.cli.tui.screens.launch.copyToClipboard`)
4. **`python/tests/unit/common/test_command_builder.py`** (extend): `writeCommandScript` writes the
   expected header + body; `offerCommandScript` behaviour unchanged

## Out of scope

- `WorkflowField.cli_flag` (superseded by the `command_builder` kwarg — see design decision)
- Save Script on the launch screen (the CLI's end-of-run re-print offers no save either)
- `mas upgrade` TUI flow (doesn't exist yet)
